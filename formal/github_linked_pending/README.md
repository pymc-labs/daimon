# Linked GitHub pending-request model

`LinkedPending.tla` asks one question: when a person finishes linking GitHub, can a chat grant request they made earlier disappear with no result in its thread, be answered twice while a claim is held, or leave a recovery half done? Requests are saved when Connect needs a link (`save_pending`), claimed by the link callback (`take`) with a token and a lease, renewed before each request, handled one at a time, answered in the originating thread, and then deleted (`resolve`). The OAuth intent is already `used` when the callback runs, so a lost request cannot be recovered by replaying the callback.

Run `FORMAL_CHECK_FILTER=github_linked_pending formal/check.sh` from the repository root with the jar specified in [`formal/README.md`](../README.md). The configs run with `-seed 1 -fp 0 -lncheck final` (one TLC worker). `-lncheck final` checks liveness once after the full search; the default checks at timed intervals and makes the count of a liveness counterexample vary between runs. `safe` and `resolve_ignores_token` take about two and a half minutes each and `live` under two (6.2 million, 6.3 million and 0.27 million states); every other config takes seconds. The default guard is 480 s (`TLC_TIMEOUT_S`).

The model follows the design in the working tree on top of `ac782e183`: claim token, heartbeat of every row the callback holds (`renew_claim`), a per-request deadline (`PER_REQUEST_DEADLINE`, 60 s, plus `FAILURE_DELIVERY_DEADLINE`, 30 s), a statement and lock deadline on the resume loop's own transactions, `take`, renewal and resolve (`DB_STATEMENT_DEADLINE`, 15 s), resolve on id and token, atomic recovery, and expiry cleanup that removes a claimed row once its lease lapsed `CLAIMED_GARBAGE_AFTER` (one hour) ago (`stores/github_linked_pending.py`, `take`). `safe` uses exactly that cleanup rule. It rests on one timing assumption: cleanup after a cancel, which no timeout caps, stays within an allowance (next section and Assumptions). The request deadline, the database deadline and the heartbeat bound the rest, and time passes in every stage of the loop, including the renewal, the post and the resolve. `lapsed_cleanup` is the same cleanup with no grace window; `no_heartbeat`, `no_deadline` and `no_db_deadline` each remove one of the three things the grace window relies on.

## Why the one-hour grace is safe, and how the model counts time

A row's lease is `claimed_until`, set to now plus `CLAIM_LEASE` (two minutes) by `take` and by every renewal. Cleanup may delete an expired row once `claimed_until` is `CLAIMED_GARBAGE_AFTER` in the past, so a row is deletable at an *age* of `CLAIM_LEASE + CLAIMED_GARBAGE_AFTER` (62 minutes) since its last renewal. A live callback renews every row it still holds before each request. Between two renewals its enforced timeouts are: the request (`PER_REQUEST_DEADLINE`, 60 s), the cancellation cleanup of a request cut off at that deadline (`settle_detached_refreshes`, up to `DETACHED_REFRESH_SETTLE_S`, 25 s), its failure line (`FAILURE_DELIVERY_DEADLINE`, 30 s), then the resolve (one database transaction under `DB_STATEMENT_DEADLINE`, 15 s), then the next renewal (one transaction, 15 s). That is `PER_REQUEST_DEADLINE + DETACHED_REFRESH_SETTLE_S + FAILURE_DELIVERY_DEADLINE + 2 * DB_STATEMENT_DEADLINE`, 145 s. Cleanup after a cancel comes on top (the database driver terminates a cancelled connection with a 2 s wait each) and no timeout caps it; the code reserves `CANCEL_CLEANUP_ALLOWANCE` (60 s) for it, an assumption. With it the gap is about 205 s, far below 62 minutes. Only the loop's own transactions (`take`, the renewal, the resolve) carry the statement deadline and an `asyncio.timeout` of it; transactions inside a request (the authority read, the recovery transaction, the linked-grant transactions) are bounded by the request deadline, which is why that deadline and the settle time are in the request stage. The module asserts that arithmetic, allowance included, at import (it also adds `CLAIM_LEASE`, which is stricter than the model needs); the assertion checks constants, not elapsed time.

The model counts time in ticks and lets time pass in every stage, each with its own bound on a per-worker stage clock `win`:

| Stage | Model bound | Code bound |
| --- | --- | --- |
| request (outcome, recovery, result post, the settle time after a cancellation, and the failure line after a timeout) | `Deadline` ticks, then `Timeout`. `Deadline` stands for the three code bounds, 60 + 25 + 30 = 115 s, plus the cancel-cleanup allowance (60 s) | `asyncio.timeout(PER_REQUEST_DEADLINE)`, then `settle_detached_refreshes` (`DETACHED_REFRESH_SETTLE_S`), then `FAILURE_DELIVERY_DEADLINE` |
| renewal transaction | `DbTicks`, then `HeartbeatTimeout` (or `RenewRaise`) | `statement_timeout` / `lock_timeout` and `asyncio.timeout`, `DB_STATEMENT_DEADLINE` |
| resolve transaction | `DbTicks`, then `ResolveTimeout` | the same |

When a stage has used its bound the `Tick` action is disabled for that worker until it acts. `WithDeadline = FALSE` removes the request bound and `DbDeadline = FALSE` removes the two database bounds (a stalled call waits without limit). A row's `age` is the ticks since `claimed_until` was last set; it saturates at `Lease + Garbage`. The renewal and the start of its request are one action: a lease cannot lapse between them. Expiry is not counted: `expires_at` can pass at any time, which over-approximates the ten-minute constant.

Scaling: `Lease = Deadline = DbTicks = 1` and `Garbage = 4`. The real ordering is `DB_STATEMENT_DEADLINE` (15 s) < `CLAIM_LEASE` (120 s) < request plus settle plus failure line plus allowance (175 s) < that plus two database calls (205 s) < `CLAIMED_GARBAGE_AFTER` (3600 s). The model collapses the three small quantities to one tick each and keeps the inequality cleanup depends on: `Deadline + 2 * DbTicks` (3) below `Garbage` (4). A shorter lease and a longer database wait than in production only add behaviours, and the stage bounds still sum to less than the grace, so the clean result is a statement about that arithmetic, not about the strict ordering of the small constants. The stricter ordering was tried (`Lease = 3`, `Deadline = 2`, `Garbage = 5`) and does not fit the time guard: `safe` passed two million states after seven minutes and `live` 1.6 million after eight. The code's assertion adds `CLAIM_LEASE` to the sum, which the model's margin (3 + 1 = 4, not below 4) does not reproduce; cleanup only needs the sum below `Lease + Garbage`.

The clean result is therefore a statement about the design's arithmetic plus the orderings of take, renewal, expiry, cleanup, crash, skip, a database timeout and a second callback, not about a measured callback duration. What it still assumes is listed under Assumptions: the deadlines are actually enforced, and an event-loop stall is crash-equivalent.

## Constants and scaling

| Quantity | Model | Source and scaling |
| --- | --- | --- |
| Requests | 2 | Smallest batch where one request can fail, be skipped or expire while another runs. Order is the take order (`expires_at`, then `id`), so request 1 runs first. |
| Workers (link callbacks) | 2, one `take` each | One callback crashes or runs slowly, a second one retakes. A worker's one take is one fresh token, so the token is the worker's name. Production has one callback per link completion. |
| `Lease`, `Deadline`, `DbTicks`, `Garbage` | 1, 1, 1, 4 ticks | `CLAIM_LEASE` 2 min, `PER_REQUEST_DEADLINE` 60 s plus `FAILURE_DELIVERY_DEADLINE` 30 s, `DB_STATEMENT_DEADLINE` 15 s, `CLAIMED_GARBAGE_AFTER` 60 min. Only `Deadline + 2 * DbTicks < Garbage` is kept (see the scaling paragraph above); the three small quantities are collapsed to one tick. The ratios differ from production (the model's grace is 4/3 of the gap, production's is thirty times); the argument depends on the inequality only. |
| Expiry | `expired` flag, set at any time | Ten minutes in code. Any ordering of expiry, lease and take is explored. |
| Replacement rows | a flag, `replSaved` | The replacement is a fresh pending row for the next link callback; its own life is not modelled. |
| Take per worker | 1 | A callback calls `take` once. |

`take`, `renew_claim`, `resolve`, the recovery transaction and `save` are each one atomic action: each is one SQL transaction in the code, and time passes before each commits (up to `DbTicks` ticks, then the timeout action instead). `Start`, `Process*`, `PrivateDeliver`, `Deliver` and `Resolve` are separate because each is a separate `await` with network or database calls between them. The renewal and the start of processing are one action; a lease cannot lapse between them in production because the renewal just set it. `delivered` saturates at 2 (the invariants only ask for at most 1). `RecoveryEnabled = FALSE` in `live` only, to keep its liveness check inside the time guard.

## Properties

| Property | Meaning |
| --- | --- |
| `NoSilentLoss` (invariant) | A row is never removed unless its request reached an outcome **and** a post to the person was attempted, **or** it expired and no live worker still intended to run it (never claimed, or its holder died, skipped it or finished with it, but not a holder that gave it up with no answer and no visible failure, as `heartbeat_break_current` does), **or** a worker that held it unfinished died or let an exception escape (the person saw a failed browser request), **or** the recovery transaction replaced it with a fresh pending row. One further clause is the state form of "will attempt": a live worker is past its renewal for the request and has not posted yet; `live` checks that this window closes (`HeldReachesOutcome`, `OutcomeReachesAttempt`). A row whose holder is alive but has not yet started it is **not** covered, because the renewal would fail and the worker would skip it: deleting such a row is the violation `lapsed_cleanup`, `no_heartbeat`, `no_deadline` and `no_db_deadline` show. Time passes during renewal, post and resolve: there is no restriction on when it may pass beyond the stage bounds. |
| `NoDuplicateDelivery` (invariant) | Two thread posts for one request only if its lease lapsed while a live worker was working on it, or after a post was tried (a crash or slow resolve between the post and the delete). Both are accepted and documented. A stale worker whose token no longer matches skips, and a second take never returns a live claim. |
| `CrashLeavesRetakeable` (invariant) | A worker's death or escaped exception never deletes the request it held: until the request expires, the row stays for a later take, or the recovery transaction replaced it, or it was answered. |
| `RecoveryAtomic` (invariant) | The original and its replacement are never both present, and the original is never gone with no replacement and no post attempt, unless it expired and was cleaned after its holder left it. |
| `HeldReachesOutcome` (temporal) | A request a worker holds reaches an outcome (a grant result, a recovery decision or a failure line) even when another request in its batch fails, unless its holder skips it. Fairness: weak fairness on the workers' own steps (`WorkerStep`); none on `Save`, `Take`, `Expire`, `Tick`. Checked with `CrashEnabled = FALSE`, `RenewException = FALSE` and `RecoveryEnabled = FALSE` (a dead or skipping worker holds nothing; the skip path is covered by `safe`; recovery is covered by the safety configs). Database timeouts stay enabled. |
| `OutcomeReachesAttempt` (temporal) | An outcome is followed by a post attempt, unless a worker skipped the request afterwards (its claim passed to another callback). Same fairness and bounds. |

`abort_batch_on_exception` is the pre-claim code, not a claim-lease variant: `take` deleted the rows it returned (`DeleteOnClaim`), the loop had no per-request `try`, so an exception left it. The failing request gets no outcome and the rest of the batch is abandoned with its rows already deleted. The exception reaches the browser, so `NoSilentLoss` is not violated (the crash clause covers it); what breaks is that held requests never reach an outcome.

`resolve_ignores_token` is clean because a resolve always follows that worker's own post attempt. A stale worker that deletes a row another worker holds only removes a request that already has a post. The other worker then skips (its renewal finds no row) or has already started and posts a second time, exactly as it would with a token check. In this model the token on resolve changes which worker wins, not safety; the token check that prevents duplicates is on the renewal (`renew_ignores_token`). Keep the token on resolve if the design wants a stale worker unable to touch a new holder's row, but do not cite this model as the reason.

`no_heartbeat`, `no_deadline` and `no_db_deadline` each remove one thing the grace window needs, and `heartbeat_break_current` removes the batch-wide failure line a failed renewal must post. Now that time passes during the renewal, `no_heartbeat` and `no_deadline` are different state graphs (53,943 and 52,838 states), but with a two-request batch the heartbeat alone still cannot be isolated: with the deadlines on, the second row's age at its start is at most one request plus one resolve plus one renewal, below the grace, so a no-heartbeat config with both deadlines on is clean here. The heartbeat matters through the batch size: without it the last row's age at its start is `(n - 1)` times the per-request gap, and `take` selects an unlimited batch, so `n` of about thirty at the real constants (`(n - 1) * 130 s` of enforced timeouts against the 62 minutes) breaks the grace; with the heartbeat the age is one gap for any `n`. A three-request config needs a larger state space than the time guard allows, so it is not pinned; the claim rests on that arithmetic and on `test_without_the_heartbeat_the_stranger_cleanup_would_delete_the_second_row`.

A heartbeat failure no longer continues the batch. It posts a failure line to every held request, resolves none and stops, so a stalled database cannot age the rows behind the failing one: after the stop nothing is waiting for a renewal, and each row has been answered. `heartbeat_break_current` is the previous code, which gave the line to the current request only and stopped: the rows behind it were abandoned with no answer and no visible failure (the browser shows success), expired, and were cleaned.

## Counterexamples in plain words

1. `lapsed_cleanup` (cleanup with no grace): a link callback takes a batch; request 2 is not started yet because request 1 is slow. Request 2 expires and its lease lapses. A second callback's `take` deletes every expired row whose lease lapsed, including request 2. The first callback then reaches request 2, its renewal does not return the row and it skips it. No outcome, no post, no crash, no row. The grace window removes this: the row is deletable only an hour after its last renewal.
2. `no_deadline` and `no_heartbeat`: the grace window is only as good as the bound on how long a live callback goes without renewing. With no per-request deadline, request 1 hangs (an unpaginated list of installations and repositories, a slow GitHub, a lock wait) for longer than the hour. Request 2's row, never renewed since the take, expires and is cleaned by another person's callback; when request 1 finally ends, request 2's renewal returns nothing and it is skipped with no line in its thread, and no crash. The deadline cuts request 1 off at 60 s with a failure line.
2a. `heartbeat_break_current`: two requests are taken. The renewal before request 1 times out. Request 1's thread gets the failure line and the loop stops; request 2's thread gets nothing, and the browser shows "GitHub linked", not an error. Request 2's row stays claimed and is never renewed; it expires and another person's callback deletes it once its lease lapsed the grace ago. The design posts the line to every held request first.
2b. `no_db_deadline`: the request deadline is in place, but the renewal before request 1 waits on a lock or a dead connection with no statement deadline. The rows age past the grace while the callback is stuck in that call; another person's callback takes and deletes the expired rows, and the stuck callback finds them gone. With `DB_STATEMENT_DEADLINE` the call fails after 15 s, the request gets a failure line (`HeartbeatTimeout`) and the batch stops with its rows still claimed, so a later take can run them within the hour, as after a crash.
3. `expiry_deletes_claimed` (`9441d430d`): the same, without waiting for the lease: a callback that took a request near its expiry loses the row to any other `take` while the request is under a live claim.
4. `delete_on_claim`: two requests are saved. The callback takes them; `take` deletes both rows. The agent lookup raises or the process exits. No outcome, no row; the person's browser shows an error and the thread never hears back.
5. `abort_batch_on_exception`: two requests are taken and deleted. The first raises; the exception leaves the loop. The browser shows an error; the second request has no outcome and no row.
6. `resolve_before_delivery`: the grant for a request succeeds and its row is deleted. The process exits before the result is posted. The grant exists, the person sees a failed browser page and never gets the line, and nothing can retake the request.
7. `take_ignores_lease`: one callback takes a request and starts it. A second callback takes the same request while the first lease is still live, and both post.
8. `renew_ignores_token`: callback A takes requests 1 and 2 and is slow on 1. The lease lapses. Callback B takes both and starts request 2. A reaches request 2, its renewal by id succeeds on B's claim, and both post for request 2.
9. `nonatomic_recovery`: a request needs a fresh GitHub link. The replacement row commits, then the process exits before the original is resolved. Both rows exist; the next callback takes both and the person gets two recovery links and two lines.
10. `delivery_failure_witness`: a request succeeds, the post to the thread fails, the failure is logged and the row is deleted. The person sees nothing. This is the one gap the model shows and the design keeps.

## Not modelled

Request content, agent identity checks, `needs_install` recovery (no replacement row; it behaves like the plain path), the life of the replacement row after it is saved (a later callback taking it, its own expiry), multiple requesters, more than two requests or callbacks (the batch-size argument for the heartbeat is arithmetic, see above), a callback that calls `take` twice, clock skew between database and process, cancellation as a separate case from a crash, the browser page text (`REQUEST_CHANGED_MESSAGES`), the second-installation result, a post that succeeded and was then cancelled by the deadline (the failure line is then a second post), the failure line's own 30-second deadline as separate ticks (inside `Deadline` for a request timeout, uncounted after a heartbeat timeout), a database timeout of `take`, of the recovery transaction or of `save` (only the renewal and the resolve have timeout actions), whether the failure lines after a heartbeat failure reach their threads (best-effort posts whose success is not tracked), and their own time (each up to `FAILURE_DELIVERY_DEADLINE`, `n * 30 s` for `n` held rows), batches longer than two requests, and a garbage collector for claimed rows that never expire (a request whose callback crashed keeps its row until it expires and a later `take` cleans it). Recovery is not explored for the legacy loop (`DeleteOnClaim`).
